# Build vs Buy for a Live RL Training Dashboard

## Executive Summary

- **Graph Is the Hard Requirement**: A 10k-100k node force simulation is fundamentally a browser rendering and layout problem, not a Python dashboard problem. Put the simulation and animation loop in the browser, send compact node/edge deltas from Python, and use level of detail, clustering, or sampling at the upper end of the range.
- **Custom React Wins the Graph**: React + Vite with a FastAPI WebSocket endpoint has the lowest architectural risk because it gives the graph its own client-side render loop and gives the RL process a purpose-built streaming channel. This is the recommended primary UI, not because it has the fewest initial lines, but because it delays the first failure to the actual graph workload.
- **Streamlit Is Possible Only as a Shell**: Streamlit uses a persistent WebSocket client-server architecture [5], and `st.fragment(run_every=...)` can update a live region without rerunning the entire app [4]. A custom component could technically run an independent browser animation loop, but the normal Python execution model and component boundary make Streamlit a poor primary surface for a continuously animated 10k+ graph.
- **Dash Is a Good Metrics Dashboard, Not a Proven Force-Graph Engine**: `dcc.Interval` supports periodic updates [8], `dcc.Graph.extendData` appends time-series points [10], and Dash WebSocket callbacks can push intermediate values [7]. Dash Cytoscape is a serious network component, but its documentation describes Cytoscape.js and does not establish WebGL rendering or a guarantee for a continuously animated 10k+ force layout [9].
- **Panel Has the Best Python-Friendly Escape Hatch**: Panel can stream Bokeh data periodically [12] and can embed JavaScript or React through `JSComponent` and `ReactComponent` [11]. That makes a custom WebGL graph feasible, but once that component is written, the project has become a custom frontend embedded in Panel.
- **W&B Should Be Bought for Tracking, Not the Graph**: W&B is strong for run history, learning curves, tables, media, and Vega custom charts [16] [17]. `wandb.Html` logs HTML content [15], but the reviewed documentation does not promise a live, continuously connected HTML application, and it does not document a native force/network graph. Use it as the experiment system of record, not as the real-time graph UI.
- **Gradio Is a Demo Surface**: Gradio supports custom components that can be packaged as Python packages [23], with frontend components commonly involving npm JavaScript [22]. That is adequate for a prototype or model demo, but a production telemetry dashboard with a high-rate graph will quickly outgrow its event and component model.
- **Hybrid Is the Best Buy Decision**: Build one small custom React graph route, keep learning and P&L curves in the same app or in W&B, and log all runs to W&B. This buys reproducibility and comparison without forcing W&B, Streamlit, Dash, or Panel to own the hardest visualization.

## The Decision Test: What Must Be True

The requirement has three different workloads. Curves are append-only time series. The graph is a stateful, high-frequency scene with a force solver, incremental topology changes, hit testing, camera state, and GPU or worker scheduling. The RL process is a long-running producer that must not be blocked by UI callbacks.

| Requirement | Appropriate transport | Where the hot loop should run | What a framework must not do |
|---|---|---|---|
| Learning curve | Batched points over WebSocket or interval polling | Plotly, ECharts, uPlot, or a small canvas/WebGL chart | Serialize the entire history every tick |
| P&L/equity curve | Append-only points plus bounded history | Browser chart | Recompute the full figure on every event |
| Growing graph | Node/edge deltas, compact binary or compressed JSON | Browser WebGL renderer and preferably a worker/GPU layout | Rerun Python and resend the entire graph every frame |
| Training control | Explicit commands and acknowledgements | FastAPI or framework WebSocket endpoint | Couple training progress to a request callback that can time out |
| Persistence and comparison | W&B, database, object storage | Offline from the animation loop | Make the visualization system the only run store |

A practical acceptance test is not simply "can it display 10,000 nodes?" It is: can it add nodes while the force simulation continues, maintain 30-60 FPS interaction on the target hardware, avoid sending the full graph on every update, and keep training alive when a browser disconnects? A static or preset-position graph may pass where a continuously animated force layout fails.

## Option Analysis and Failure Cases

### 1. Custom React + Vite + FastAPI: Build the Critical Path

The custom route separates concerns cleanly. The RL process publishes events to a FastAPI WebSocket endpoint. A browser store applies node and edge deltas. A worker or GPU-capable graph library owns force integration, while React owns controls and selected-node details rather than re-rendering every node on every tick. Curves can use a normal chart library and update by appending bounded batches.

This is not zero work. The team must implement authentication, reconnect and replay, backpressure, schema versioning, training-process supervision, and a policy for browser disconnects. FastAPI's basic WebSocket pattern also has deployment implications: an in-memory connection list only works within one process, so multi-worker or multi-instance deployment needs a broker or a single stream service. That is an engineering risk to design explicitly, not a reason to choose a framework that hides the graph.

The right performance contract is delta-based. Send `add_nodes`, `add_edges`, attribute changes, metric batches, and occasional snapshots. Do not send the complete 100k-node graph every training step. For 10k nodes, full interaction may be practical on modern desktop hardware if the graph is sparse and labels are selective. For 100k, require clustering, viewport culling, level of detail, or a GPU layout; displaying every label and simulating every pairwise force is not a realistic default.

**Case study: the useful comparison is not Python versus JavaScript.** Reflex documents a React frontend, FastAPI backend, Python state, and WebSockets [20]. That is effectively the same transport shape as the recommended custom stack. The difference is how much UI lifecycle the framework owns. If the graph needs imperative typed arrays, worker messages, and a render loop outside normal reactive state, direct React makes that boundary explicit and easier to profile.

### 2. Streamlit: Excellent Control Surface, Awkward Animation Host

Streamlit's architecture is more capable than the common caricature. Its server uses Tornado WebSockets, maintains a persistent two-way channel, and gives each browser tab its own session [5]. Fragments improve the situation: widget interaction inside a fragment reruns only that fragment, and `run_every` can update it without user interaction [4] [4] [4]. That is enough for live loss and P&L panes, status, controls, and periodic snapshots.

The limit is that automatic fragment reruns are still sequential [4]. A custom component follows the normal Streamlit execution flow [4]. Therefore, a continuously animating WebGL graph is technically possible only if the component starts its own browser animation loop and receives occasional state deltas. A Python loop that reruns at frame rate is the wrong design. The component API is a transport and lifecycle boundary, not a GPU graph engine.

The real user evidence is consistent with that caution. Streamlit issue #7926 is labeled performance/bug/question and reports that the website takes a long time to run and that clicking rerun hangs at "Please wait" [1] [1]. This is not a 100k-node benchmark and should not be misrepresented as one. It is a concrete failure mode: rerun latency and incomplete reproduction make a high-rate animation loop difficult to diagnose.

`streamlit-agraph` is particularly risky for a production choice. Its README calls it a Streamlit graph visualization based on `react-graph-vis` [3] [3], but also says it is not working after the agraph 2.0 update [3]. `streamlit-flow` is more appropriate for node-editor and workflow diagrams. `st.plotly_chart` and `streamlit-echarts` are reasonable curve panes, but they do not solve force layout. The best Streamlit design is a metrics/control shell plus a custom graph component that owns the animation. If the graph is the product, start elsewhere.

### 3. Dash: Strong Streaming Primitives, Unproven Graph Scaling

Dash offers a better documented live-update path than a naive callback loop. `dcc.Interval` triggers callbacks periodically [8], and `dcc.Graph.extendData` appends points rather than replacing the entire trace [10]. That is a good fit for learning and equity curves. Dash's WebSocket callbacks can push intermediate values with `set_props`, and the callback can continue to a final state [7].

The graph distinction matters. Dash Cytoscape renders Cytoscape.js and integrates network events with Dash layouts and callbacks [9] [9]. It may be a perfectly good choice for a 1k-10k graph with preset positions, limited labels, and batched updates. The evidence reviewed does not establish WebGL rendering or continuous 10k+ force animation. I would not approve it for the stated requirement without a target-hardware prototype using the actual topology and edge rate.

Dash's new WebSocket mode also has operational constraints. Async callbacks run on the event loop, while synchronous persistent callbacks use a shared thread pool. The documented default is four workers, and a persistent synchronous callback can exhaust that pool [7]. The design should therefore use async producers or an external stream, keep callbacks short, and let the browser animate. Dash Open Source is permissively licensed [6], but Plotly's own repository distinguishes local Dash Open Source from organization-wide Dash Enterprise [24]. The Enterprise distinction is a deployment and governance trade-off, not a reason to buy Enterprise for graph rendering.

### 4. Panel: The Most Credible Python-First Hybrid

Panel's Bokeh server model is a good match for periodic telemetry. Its documentation shows per-session periodic callbacks, a 200 ms example, and start/stop controls [12]. The streaming example uses `ColumnDataSource.stream` from a periodic callback [13]. This is a strong fit for bounded curves, sampled graph statistics, and training controls.

The deciding feature is the escape hatch. Panel's `ReactComponent` extends `JSComponent`; its ESM path accepts JavaScript, JSX, TypeScript, and imported dependencies [11]. A team can therefore place a real WebGL graph library in the browser while retaining Panel for Python layout and metrics. The cost is that the graph is now a separately authored frontend component with its own state, build assumptions, and testing. Panel reduces the shell cost, not the core graph cost.

Panel is the best choice if the team is strongly Python-first, the graph is one panel among many, and a custom ESM component is acceptable. It is not the best choice if the graph needs deep React ecosystem integration, complex client-side state, or maximum control over GPU scheduling. In that case, direct React is simpler because there is one frontend runtime instead of Panel, Bokeh, and a custom renderer cooperating.

### 5. Gradio and W&B: Buy the Easy 80 Percent, Do Not Pretend It Is the Hard 20 Percent

Gradio's custom-component story is real: components can be created and published as Python packages [23], and the frontend ecosystem uses npm JavaScript [22]. That makes a graph technically possible. It does not make Gradio a natural high-rate dashboard runtime. The first break is likely to be event and state synchronization, serialization, reconnect behavior, or the component lifecycle. Use it for a training demo, a human-in-the-loop control surface, or a prototype that proves the RL process.

W&B is the opposite trade-off. It is a strong buy for run identity, history, metrics, tables, media, and comparison. Workspaces create panels around logged keys [16], and custom charts can query run history and use Vega specifications [17] [17]. The result is valuable for post-run analysis and live-ish metric monitoring, but it is not evidence of a native force graph.

`wandb.Html` accepts a path, literal HTML, or an IO object [15]. W&B also documents custom HTML panels on a run page [18]. That supports attaching a visualization artifact or an external app shell. It does not, in the reviewed documentation, guarantee that arbitrary JavaScript maintains a live WebSocket connection, survives report rendering and security policies, or updates during an active run. A Vega chart is interactive in the W&B UI [17], but a continuously animating WebGL force scene is a different execution model.

**Case study: W&B is best used as the durable layer.** The documentation explicitly models scalar history, tables, and media as logged run data [18] [17]. That is exactly what should remain after a browser disconnects. The graph UI should consume the same event stream in real time and optionally log snapshots or graph summaries to W&B. This avoids making an experiment tracker responsible for a low-latency, stateful scene.

| **NiceGUI** | Fast Python control panels and timer-driven displays | Custom JavaScript required | Mature React/WebGL ecosystem and explicit client-state architecture |
| **Solara** | Reactive Python data applications | Custom frontend required | Predictable high-rate imperative rendering path |

| **Evidence** | SQL/data products and report-style dashboards | Plugin or external embed required | Native streaming and training-process control |
| **Rerun** | Streaming RL observations, rollouts, and multimodal replay | Promising telemetry buy, not proven force-graph buy; its SDK is for logging, storing, querying, visualizing, and training [21] | A purpose-built knowledge-graph interaction model |

The non-obvious alternative is Reflex. Its documented architecture is already React plus FastAPI plus WebSockets [20], so it can reduce application-shell code without changing the graph recommendation. Rerun is attractive when the RL team needs replayable multimodal data, but it should be evaluated as an observability layer. NiceGUI's timer is useful for periodic measurements, but periodic callbacks are not a substitute for a client-owned force simulation.

## Recommended Architecture

1. **Training producer**: The RL process writes metric batches and graph deltas to a durable queue or stream. It must continue when no browser is connected.
2. **FastAPI stream service**: Expose authenticated WebSocket subscriptions. Include run ID, sequence number, schema version, timestamp, and event type. Keep a bounded replay buffer so reconnecting clients can catch up.
3. **React graph client**: Maintain nodes, edges, positions, selection, camera, and simulation state outside ordinary React render churn. Render nodes and edges with a WebGL-capable library. Use a worker or GPU layout where supported.
4. **Backpressure and LOD**: Batch updates, cap edge labels, cluster distant subgraphs, cull off-screen detail, and freeze stable regions. At 100k nodes, make aggregate and neighborhood views first-class rather than promising full-detail interaction.
5. **Curves**: Append bounded batches for reward/loss and P&L/equity. Keep raw history in W&B or a database; keep only the visible window in the browser.
6. **W&B integration**: Log run configuration, scalar history, periodic graph snapshots or summary statistics, artifacts, and evaluation media. Use W&B for comparison and audit, not for the frame loop.
7. **Optional Python shell**: If rapid internal delivery matters more than frontend control, put Panel or Reflex around the same graph component. Do not duplicate graph logic in Streamlit, Dash, and W&B.

## Build-vs-Buy Recommendation and Explicit Losses

**Recommendation: build the graph application, buy the experiment system.** Build a small React + Vite graph frontend with a FastAPI stream endpoint. Buy or retain W&B for experiment tracking, metrics, tables, artifacts, and run comparison. If a Python-first shell is strategically important, choose Panel or Reflex, but embed the same graph component rather than relying on native framework widgets.

| If you do not choose... | What you lose |
|---|---|
| **Custom React + FastAPI** | Faster initial prototyping and less frontend ownership. You may save weeks at the start, but you trade them for a high-risk rewrite when the graph becomes the product. |
| **Streamlit** | The shortest Python path to controls, status, and quick charts. You also avoid Streamlit's useful fragments and WebSocket architecture, but you give up little graph capability because the graph still needs custom JavaScript. |
| **Dash** | Excellent callback, Plotly, and enterprise deployment conventions. You give up a mature metrics dashboard if you reject it, but you avoid relying on an unproven Cytoscape/WebGL combination for the hardest requirement. |
| **Panel** | A strong Python-native composition model, Bokeh streaming, and a documented ESM escape hatch. The cost of rejecting it is mostly shell productivity, not graph capability. |
| **Gradio** | Very fast model demos and shareable interfaces. You lose the easiest demo path, while avoiding a component/event model that is less natural for telemetry-heavy production dashboards. |
| **W&B** | Durable run comparison, collaboration, artifacts, and a mature metrics UI. Do not reject it; use it for the part it is designed to do. |
| **Reflex/NiceGUI/Solara/Shiny** | Python-first application speed and reactive controls. You still need to write and operate the graph component, so the saving is mainly shell code. |
| **Rerun** | Potentially excellent streamed RL and multimodal replay. Reject it only if the knowledge graph interaction model is more important than replay and sensor-style visualization. |
| **TensorBoard** | Familiar scalar training dashboards and plugin conventions. You avoid a disk/plugin-oriented architecture for a graph that needs low-latency browser state. |

The go/no-go gate should be a one-week prototype using the actual graph degree distribution, node arrival rate, edge arrival rate, target browser, and target GPU. Measure frame time, memory, WebSocket bandwidth, time to apply a delta batch, reconnect recovery, and RL throughput. If the graph passes only with clustering or preset positions, make that a product requirement rather than hiding it behind a framework choice.

## Synthesis

Across all options, the mechanism is consistent: Python is excellent at producing training state, but a 10k-100k animated graph needs a client-owned scene graph and render loop. Frameworks differ mainly in how much shell code they save before the custom component boundary appears. Streamlit saves Python UI code but still reruns Python; Dash improves live callbacks but still serializes component properties; Panel exposes a clean ESM boundary but leaves the graph authoring to you; Reflex provides a React/FastAPI shape but does not eliminate graph engineering.

The trade-off is therefore not "build everything" versus "buy everything." It is **build the scarce capability and buy the commodity capability**. The scarce capability is a robust, profiled, delta-driven graph renderer. The commodity capability is run tracking, scalar history, curve comparison, media, and artifacts, where W&B is the stronger buy. A custom React graph plus W&B produces the least duplicated work and the clearest failure boundaries.

The main tension is between prototype speed and irreversible architecture. Streamlit, Gradio, and notebook-oriented tools can produce a convincing demo quickly. That demo may conceal the exact costs that appear later: full-state serialization, rerun latency, component lifecycle bugs, callback queues, graph layout stalls, and browser memory. Conversely, building a complete custom platform before measuring the graph is wasteful. The disciplined compromise is a small custom graph spike, a durable W&B logging path, and a thin shell around both.
